# ۰۲ — مدل دامنه و زبان مشترک (Domain Model)

> **هدف این سند:** یک زبان واحد فارسی↔انگلیسی برای کل تیم و کل لایه‌ها (پروتوتایپ، API، دیتابیس)، به‌همراه قواعد شکست‌ناپذیر دامنه (invariants) و چرخه‌های حیات موجودیت‌ها. هرجای اسناد دیگر واژه‌ای ابهام داشت، مرجع همین‌جاست.

---

## ۱. لایه‌های هویت کالا — مهم‌ترین تصمیم دامنه

iMach کالا را در **سه لایه** می‌بیند؛ به‌هم‌ریختن این لایه‌ها ریشهٔ اکثر باگ‌های داده‌ای است:

```
Category (دستهٔ مرجع — درخت جهانی)
   └── Good (کالا/نوع کالا — کلاس قابل‌مبادله: «برنج هاشمی»)
          └── Product (محصول — SKU برند×مشخصات: «تن ماهی مکنزی ۲۵۰ گرم»)
                 └── Listing (آگهی — فروشنده × کالا × واریانت: «پخش برنج پارس / کیسهٔ ۱۰ کیلویی»)
```

| لایه | تعریف | چه چیزهایی روی آن زندگی می‌کند | مثال |
|---|---|---|---|
| **Good** | کلاسِ قابل‌مبادلهٔ کالا — واحد رسمی مبادله | واحد رسمی، دستهٔ مرجع، نام‌ها/مترادف‌ها، وضعیت باغبانی | «برنج هاشمی» · واحد: گونی |
| **Product** | SKU مشترک برند×مشخصات بین همهٔ فروشندگان | برند، بارکد، مشخصات استاندارد، عکس مرجع | «برنج هاشمی برند فجر — ۱۰ کیلویی» |
| **Listing** | ردیف واقعی فروش/خریدِ یک کسب‌وکار | قیمت، موجودی، حداقل سفارش، بسته‌بندی، عنوان شخصی، توضیحات فروشنده | «پخش برنج پارس — کیسهٔ ۱۰ کیلویی — ۵۹۵٬۰۰۰» |

**قاعدهٔ لایه‌ای:** برند روی Good نمی‌نشیند (همین کلاس با ده‌ها برند مبادله می‌شود)؛ مشخصات ساختاریافته روی Product؛ قیمت/موجودیِ فروشنده همیشه روی Listing.

## ۲. واژه‌نامهٔ دوجانبه (Ubiquitous Language)

| فارسی (UI) | انگلیسی (کد/مدل) | تعریف یک‌خطی |
|---|---|---|
| کالا / نوع کالا | `Good` | کلاس مرجع قابل‌مبادله؛ واحد رسمی مبادله روی آن تعریف می‌شود |
| دستهٔ کالا | `Category` | گرهٔ درخت مرجع (۳–۴ سطح) + اسکیمای ویژگی‌ها (attrs) |
| محصول | `Product` | SKU مشترک برند×مشخصات؛ برای فروشندگان برنددار |
| برند | `Brand` | هویت تجاری قابل‌مالکیت؛ اختیاری |
| واحد / واحد پایه | `Unit` | واحد اندازه‌گیری با سه دامنه (پایه/مصرفی/عمده) و نسبت تبدیل |
| آگهی | `Listing` | ردیف فروش/خرید یک کسب‌وکار برای یک کالا×واریانت |
| واریانت / بسته‌بندی | `variantKey`/`baseQty` | تمایز ردیف‌های یک کسب‌وکار برای همان کالا (بستهٔ ۱۰kg در برابر ۵۰kg) |
| کسب‌وکار | `Business` | موجودیت تجاری خریدار-و-فروشنده؛ همهٔ تراکنش‌های B2B به آن وصل‌اند |
| دستیار فروش/خرید | Arm (`SELL`/`BUY`) | زمینهٔ کاری درون یک کسب‌وکار؛ قابل خاموش/روشن |
| کاتالوگ | Catalog (نمای فروش) | مجموعهٔ آگهی‌های فروش یک کسب‌وکار + ویترین عمومی آن |
| لیست خرید | Buy List (`WatchedGood`+) | کالاهایی که خریدار رصد می‌کند + درخواست‌های جاری |
| لیست مقایسه | Comparison List | قیمت‌های دنبال‌شدهٔ یک کالا بین فروشندگان، رتبه‌بندی نرمال‌شده |
| تابلوی تأمین | Supply Board | همهٔ فروشندگان فعالِ یک کالا + برچسب رابطه |
| دنبال‌کردن کاتالوگ / ذخیره | `Follow` (Saver) | یال خریدار→کاتالوگ فروشنده؛ منبع و نوع مشتری روی همین یال |
| دنبال‌کردن قیمت | `WatchedGood` | رابطهٔ خریدار↔کالا در لیست خرید (good-level، نه فروشنده-level) |
| گوش به زنگ | `NeedAlert` | اشتراک فروشنده به نیاز خریدار برای یک کالا |
| درخواست خرید (RFQ) | `Inquiry` (+ `rfqGroupId`) | استعلام قیمت یک کالا با حجم/مهلت؛ گروهی به چند فروشنده |
| پیشنهاد قیمت | `Offer` | پاسخ فروشنده به درخواست؛ امتیاز تطبیق روی آن ذخیره می‌شود |
| بهترین آیمچ | Match Score | امتیاز ترکیبی رتبه‌بندی پیشنهادها (قیمت/نزدیکی/سابقه/احراز) |
| فروشندهٔ ویژه | Sponsored (`Promo`) | جایگاه تبلیغاتی شفاف — رتبهٔ طبیعی مستقل از پرداخت |
| کمپین / تبلیغ هدفمند | `Promo.type` | دو نوع تبلیغ: گسترده در بخش کمپین‌ها / جراحی‌وار روی کالای هدف |
| کیف پول | `Wallet` (+`WalletTxn`) | موجودی تومانی برای مصرف تبلیغ؛ رویداد-محور |
| نوع مشتری | `custType` (گذری/همکار/قراردادی) | برچسب فروشنده روی مشتری؛ ورودی موتور تخفیف |
| تخفیف (سه‌سطحی) | `DiscountRule` | کاتالوگ › گروه کالا › خودِ کالا؛ خاص‌تر برنده |
| تخفیف پلکانی/حجمی | `tiers` | پله‌های تخفیف بر حجم همان کالا در سفارش |
| بازدید / مشاهدهٔ کامل | `VIEW` event | رسیدن به قیمت/موجودی در صفحهٔ کالا؛ واحد شارژ تبلیغ |
| ذخیره‌کننده | Saver (`Follow`) | کسی که کاتالوک را ذخیره کرده — یال رشد |
| نظرات و امتیاز کاتالوک | `CatalogReview` | نظر+امتیاز خریدار دربارهٔ کاتالوگ فروشنده + پاسخ فروشنده |
| حضور / آنلاین | `Presence` | وضعیت لحظه‌ای آنلاین بودن برای تصمیم شروع چت |
| کارهای امروز | Tasks | کارتابل اکشن‌محور هر دو دستیار |
| تاریخچهٔ رویدادها | `ListingEventLog` | خط زمانی تعامل‌ها با یک کالا (بازدید/رصد/استعلام/گفتگو) |
| بازخورد/پرسش و پاسخ | `FeedbackPost` | پست کاربران دربارهٔ دستیارها با لایک/پاسخ تیم |
| ارجاع / دعوت | `ref` (`User.referredBy`) | رشد ویروسی با پاداش کیف پول |

## ۳. روابط کلیدی

```
User 1─n Business 1─n Listing n─1 Good n─1 Category
                     Listing n─1? Product n─1? Brand
Business 1─1 Wallet · 1─n Promo ── n─1 Listing
Business(SELL page) 1─n Follow n─1 Business(BUY page)          ← ذخیره/دنبال‌کردن کاتالوگ
Business 1─n WatchedGood n─1 Good                              ← دنبال‌کردن قیمت (good-level)
Business 1─n Inquiry(buyer) / Inquiry(seller) ── n─1 Listing   ← درخواست خرید
Business 1─n Offer(buyer/seller) ── n─1 Listing                ← پیشنهاد
Business A ↔ Business B : Thread 1─n Message                   ← گفتگو کاری
Business 1─n CatalogReview(target) · author=Business/User
Business 1─n NeedAlert(seller) ── buyer+good                   ← گوش به زنگ
Listing 1─n PriceLog · 1─n ListingEventLog · 1─n File(gallery)
User 1─n Contact · 1─n Notification · 1─n PushSubscription
```

**توجه:** در MongoDB روابط app-side join می‌شوند؛ لایهٔ داغ (`Listing`) snapshot جغرافیایی و شمارنده‌های denormalized را خودش حمل می‌کند تا موتور تطبیق بدون join فیلتر کند.

## ۴. ناوردایی‌های دامنه (Invariants) — نقض = باگ

1. **یکتایی آگهی:** `(businessId, goodId, variantKey)` یکتاست — یک فروشنده برای هر بسته‌بندیِ هر کالا حداکثر یک ردیف دارد.
2. **قیمت همیشه به واحد رسمی Good است:** قیمت/موجودی/حداقل سفارش/حجم همه به `Good.unit` (مثلاً «هر گونی»)؛ مقایسهٔ بین واریانت‌ها فقط از راه `pricePerBaseMinor` (سند ۰۴).
3. **تطبیق هرگز Product نمی‌خواند:** خریدارِ بی‌برند نباید فروشنده‌های مرتبطِ برنددار را از دست بدهد؛ رتبه همیشه Good-level است.
4. **رتبه پولی نیست:** پرداخت فقط دیده‌شدن می‌خرد؛ جایگاه تبلیغی همیشه برچسب شفاف دارد.
5. **خریدار و فروشنده یک موجودیت‌اند:** هر Business هر دو بازو را دارد (حتی اگر یکی خاموش باشد)؛ هیچ‌جا «نقش» جای «بازو» را نمی‌گیرد.
6. **معامله بیرون از سیستم:** سیستم فقط «یافتن/اعتمادسازی» می‌فروشد؛ هیچ مدل سفارش/فاکتور برای مبلغ کالا وجود ندارد.
7. **حداقل یک دستیار روشن:** خاموشی هر دو بازوی یک کسب‌وکار در لایهٔ API رد می‌شود.
8. **باغبانی مرجع‌ها:** Good/Brand/Product با الگوی find-or-create و نرمال‌سازی متن یکتا می‌شوند؛ ردیف PROVISIONAL برای همه قابل‌استفاده است و فقط در صف ادمین می‌ماند (merge/حذف ادمین‌دار).
9. **پولِ خرج‌شده همیشه ردّپا دارد:** هر کسر از کیف یک رویداد با مرجع (کمپین/رسید/معرفی) است؛ برگشت بودجه = تراکنش REFUND، نه پاک‌کردن.
10. **حذفِ نرم:** «عدم نمایش» آگهی، رصدها/تاریخچه/امتیازها را نگه می‌دارد؛ upsert ردیفِ پنهان را زنده می‌کند. حذف فیزیکی فقط برای موجودیت‌های بی‌تاریخچه (مثلاً مخاطب شخصی) مجاز است.
11. **متن‌های مالک عیناً:** جملاتی که مالک صریح نوشته، بدون بازنویسی وارد UI می‌شوند (سابقهٔ فازهای ۲۲–۳۶).
12. **هرگز امکانی بدون حکم مالک حذف نمی‌شود** — قاعدهٔ طلایی جاری از فاز ۲۵.

## ۵. چرخه‌های حیات (State Machines)

### ۵.۱. آگهی (Listing)
```
        saveListing (upsert زنده‌کننده)
  [نوجوان] ─────────────► فعال ───────────► عدم نمایش (hidden)
                           │ │                    │ «نمایش مجدد»
                اتمام موجودی◄─┘ stock=0            └──────► فعال
                           │    (کاتالوگ می‌ماند، استعلام بسته، دنبال‌کننده مطلع)
                           └─ حذف منطقی (softDelete) → تاریخچه می‌ماند
```
«اتمام موجودی» حالتِ نمایشی روی `stock=0` است، نه وضعیت جدا؛ با شارژ موجودی خودکار برمی‌گردد.

### ۵.۲. درخواست خرید (Inquiry / RFQ Group)
```
NEW ──(پاسخ فروشنده: Offer)──► ANSWERED ──(مهلت تمام)──► EXPIRED
 │                               │
 │(کاربر: متوقف)                 │(کاربر: بایگانی)
 ▼                               ▼
STOPPED ──(شروع مجدد)──► NEW    ARCHIVED ──(درخواست مشابه)──► فرم ۱۲ prefilled
```
- مهلت از `expiresAt` محاسبه می‌شود؛ منقضی‌شده برای فروشندگان دیگر نمایش داده نمی‌شود.
- یک «درخواست گروهی» = چند ردیف Inquiry با `rfqGroupId` مشترک؛ کارتِ واحد در ۱۱/۳۶.

### ۵.۳. پیشنهاد (Offer)
```
ایجاد (موتور یا دستی) → [بدون وضعیت] → INTERESTED | CONTACTED | REVIEWED   (خصوصیِ خریدار)
```
وضعیت‌ها فقط چشم خریدار را راهنمایی می‌کند؛ فروشنده آن‌ها را نمی‌بیند.

### ۵.۴. کالا/برند/محصول مرجع
```
SEED/USER ایجاد → ACTIVE ⇄ PROVISIONAL ──(merge ادمین)──► MERGED → اشاره‌ها به بازمانده
```

### ۵.۵. کمپین (Promo)
```
ایجاد (بودجه/مدت) → فعال ──(بودجه تمام)──► متوقف-خودکار ──(شارژ)──► فعال
                        ──(توقف دستی)──► متوقف ──(راه‌اندازی دوباره)──► فعال
                        └─(مدت تمام)──► پایان (بودجهٔ مانده: REFUND)
```

### ۵.۶. نوع مشتری روی یال Follow
`null/گذری ⇄ همکار ⇄ قراردادی` — تعیین‌کنندهٔ اختصاصی فروشنده است؛ اثر زنده روی قیمتِ نمایشیِ آن خریدار.

## ۶. قواعد کسب‌وکار تأییدشدهٔ مالک (منتقل از فازهای ۲۲–۳۶)

1. **تخفیف سه‌سطحی:** اولویت «کالا › گروه کالا › کاتالوگ»؛ سه‌ورودی هم‌بسته (درصد/مبلغ/قیمت نهایی) در سطح کالا؛ سطح خاص‌تر فقط override نگه می‌دارد.
2. **قاعدهٔ سبد چندکالایی:** پلهٔ حجمی بر حجمِ «همان کالا» در سفارش حساب می‌شود، نه جمع سبد.
3. **تعریف «مشاهدهٔ کامل»:** رسیدن به قیمت/موجودی در صفحهٔ کالا — مبنای شارژ تبلیغ.
4. **دسترسی سه‌سطحی ابزار تبلیغ:** پروفایل / شیت تنظیمات کاتالوگ / سطح کالا — کاربر همه‌جا به تبلیغ می‌رسد.
5. **کیف پول واحد مصرف هر دو نوع تبلیغ است** و شارژ فقط از صفحهٔ ۲۹/درگاه.
6. **«عدم نمایش» ≠ «اتمام موجودی»:** اولی پنهان‌سازی کامل با حفظ رصد، دومی برچسب در کاتالوگ با اطلاع دنبال‌کنندگان.
7. **آمار کالا از ابتدای ثبت جمع می‌شود** («نتایج حضور در آیمچ»)، نه پنجرهٔ ۳۰روزه.
8. **نقش کاربر در کسب‌وکار** (۷ فروش / ۴ خرید) صفت نمایشی است، نه مجوز — همهٔ اعضای یک کسب‌وکار با یک حساب مالک عمل می‌کنند (فعلاً).
9. **وضعیت آنلاین** در کاتالوگ عمومی/جزئیات/لیست خرید عمومی/گفتگوها دیده می‌شود — انگیزهٔ ماندگاری آنلاین.
10. **کسب‌وکار فعال تعیین‌کنندهٔ زمینهٔ کل سیستم است** (کاتالوگ/کارها/پیام‌ها/کیف) — تعویضش سوییچ زمینه است نه خروج.

## ۷. تصمیم‌های باز دامنه‌ای

| # | موضوع | گزینه‌ها | پیشنهاد |
|---|---|---|---|
| D-1 | نقش‌ها (rolesell/rolebuy) فقط نمایشی بمانند یا مجوز واقعی شوند | نمایشی / مجوز ساده (دید-ویرایش) | MVP: نمایشی؛ مجوز فاز تیمی |
