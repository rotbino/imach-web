بله. با توضیحاتی که دادی، من پرامپت رو صرفاً به «مهاجرت UI» محدود نمی‌کنم؛ باید به GLM بگه **مالک نتیجه نهایی است، نه روش مهاجرت**. همچنین چند نکته را نسبت به پرامپت قبلی تغییر می‌دهم:

* Prototype = **Visual Source of Truth**
* Backend فعلی = **Business Logic / Data Source of Truth**
* هیچ داده‌ای نباید در مهاجرت از بین برود.
* قبل از هر migration، backup واقعی و قابل‌بازگشت از DB.
* فازها باید **قابل اجرا و قابل تست** باشند، نه صرفاً milestone کدنویسی.
* Performance، SEO، Security و PWA از ابتدا جزو معماری باشند، نه مرحله آخر.
* GLM اجازه دارد معماری فعلی را تغییر دهد، ولی فقط اگر نتیجه بهتر شود.
* ظاهر Prototype نباید قربانی «تمیزتر کردن کد» یا «استفاده اجباری از Tailwind/shadcn» شود.
* در عین حال، نباید Prototype را کورکورانه به React تبدیل کند؛ هرجا UX ناقص است باید **رفتار را کامل کند بدون تغییر هویت بصری**.
* برای پروژه‌ای با این اندازه، باید به GLM دستور داد قبل از کدنویسی **کد، Prototype و Backend را audit کند و نقشه مهاجرت بسازد**.

پرامپت زیر را عمداً طولانی نوشته‌ام، چون اینجا طولانی بودن پرامپت ارزش دارد. بهتر است آن را به‌عنوان **System/Project Prompt اصلی GLM** بدهی.

# 7. بسیار مهم: Database Safety

قبل از هر تغییر جدی در Backend یا Database:

## ابتدا از Database Backup بگیر.

Backup باید واقعی، قابل بازیابی و خارج از مسیرهای موقت باشد.

Backup را در ساختار مناسب پروژه Backend نگهداری کن، مثلاً:

```text
backend/
  backups/
    migration/
      YYYY-MM-DD/
```

یا ساختاری که برای پروژه مناسب‌تر تشخیص می‌دهی.

### قوانین:

* قبل از migration schema backup بگیر.
* قبل از migrationهای destructive backup بگیر.
* قبل از تغییرات مهم داده backup بگیر.
* هیچ جدول یا داده‌ای را بدون دلیل حذف نکن.
* هیچ داده‌ای را overwrite نکن مگر اینکه migration دقیقاً کنترل شده باشد.
* migration باید reversible باشد هرجا که منطقی است.
* قبل از destructive migration بررسی کن چه داده‌هایی تحت تأثیر قرار می‌گیرند.
* بعد از migration integrity check انجام بده.

## از دست رفتن حتی یک بخش مهم از Data قابل قبول نیست.

### یک نکته مهم درباره این پرامپت

من عمداً یک بخش را با پیشنهاد قبلی GLM **تغییر دادم**: نگفتم «CSS پروتوتایپ را کورکورانه ۱:۱ کپی کن». قانون بهتر این است:

**Visual Source of Truth = Prototype، ولی Implementation Source of Truth = بهترین معماری Production.**

این تفاوت مهم است. اگر GLM مجبور شود عیناً CSS یک فایل Prototype را به پروژه Production تزریق کند، ممکن است بعداً به CSS debt، specificity conflict و نگهداری سخت برسید. چیزی که باید **۱:۱ بماند خروجی بصری و رفتار UI است، نه الزاماً ساختار CSS داخلی**.

همچنین من پیشنهاد «همه‌چیز را اول Mock کن» را هم کنار گذاشتم. برای پروژه‌ای که Backend واقعی، Prisma و منطق تطبیق دارد، بهتر است هر Vertical Slice خیلی زود به دیتای واقعی وصل شود؛ و فقط جاهایی که Backend هنوز قابلیت لازم را ندارد Mock موقت داشته باشند.

**و یک نکته امنیتی بسیار مهم:** Backup دیتابیس را داخل Git repository نگذار، حتی اگر GLM در پرامپت پیشنهاد کند. اگر منظورت از «در پروژه بک پوش کنه» صرفاً نگهداری محلی در فولدر `backups/` است، مشکلی نیست؛ ولی این فولدر باید در `.gitignore` باشد. Backup دیتابیس حاوی داده واقعی است و نباید وارد Git یا repository آنلاین شود.

یک قانون خیلی مهم که یادم نرفته هم بگم. بعدم اگر نیاز شد باید بتونم رنگهای تم رو از طریق متغیرها تغییر بدم
تم باید کاملا تم تاریک رو هم پوشش بده. کاربر از طریق پروفایل خودش بتونه بین تم تاریک و عادی سویچ کنه. و حتی رنگ تم دلخواه خودش رو برای محیط خرید یا فروش انتخاب کنه. هم عالی میشه
یه موضوع مهم که شاید چت جی بی تی یادش رفته باشه بهت بگه اینه،که کدنویسی و کامپوننت ها طوری باشه که اگر زمانی تصمیم گرفتیم یوآی رو کاملا عوض کنیم با هزینه و زمان کمتری اینکارو انجام بدیم.
و قطعا یه چیزی رو هم یادش رفته بگه. که آیمچ همانطور که در کدهای قدمی هم مشخصه قراره یه برنامه بین المللی باشه که  بنابراین باید چند زبانگی و چند ارزی رو چه در فرانت چه در بک و چه در دیتابیس باید ساپورت کنه.  و در فاز اول سه زبان فارسی و انگلیسی و عربی رو ساپورت کنه. 
همچنین ما باید سیستم ارزی داشته باشیم که یک ارز بعنوان مرجع پایه باشه.  و کاربر به دلخواه بتونه برای سیستم خودش در پروفایل ارز خودش رو انتخاب کنه.
تمام این موارد باید با انتخاب کشور ست بشه مثل زبان و ارز رایج هر کشور و رایت تو لفت بودن هم به زبان هست. کاربر از هر کشوری که وارد میشه اون باید کشور پیشفرضش انتخاب بشه اما کاربر اگر خواست بتونه تغییر بده. زبان و ارز رو هم به دلخواه بتونه تغییر بده . که این ارز در کاتالوگ و تمام سیستمش میاد.
همچنین واحدها، گروهها، لوکیشن ها مثل شهرها و لوکیشن دقیق اینها از مسائل یه اپلیکیشن بین المللی هستن که باید هم چند زبانگی و هم بین المللی بودن رو ساپورت کنن.
غیر از ایران فعلا قرار نیست ما جایی پرداخت داشته باشیم اما می تونیم بسترش رو بزاریم و اگر بعدا نخواستیم توی تنظیمات ادمین برداریم. برای داشتن اعتبار برای هزینه مثلا در تبلیغات حتما لازم نیست کاربر پول پرداخت کنه بلکه می تونه مثلا با دعوت از کاربران جدید به آی مچ اعتبار بگیره. و این اعتبار رو در تبلیغات هزینه کنه. راه دوم هم که خرید اعتبار با پول هست. ولی در کشورهای دیگه غیر از ایران چون فعلا پرداخت نداریم کاربر می تونه با دعوت از دیگران و برخی فعالیت های مفید دیگه اعتبار کسب و کنه و در تبلیغات استفاده کنه. این کمک می کنه تا سیستم ما بصورت بین المللی هم کم کم رشد کنه
دقت کن که کار مهاجرت رو قرار نیست به یکباره انجام بدی. می تونی توی چند  و چندین فاز انجام بدی و در هر فاز کاملا با حوصله و درست جلو بری. مهم نیست چند فاز باشه اما باید برنامه ریزی این فاز رو بنویسی و به منم بدی که هر بار بفهمم چه فازی رو اجرا کردی و هر بار که سندباکست ریست شد بهت اون فازها وبرنامه ریزی خودت رو بدم تا بتونی از فاز بعدی ادامه بدی تا در نهایت کار مهاجرت تکمیل بشه
در نهایت هم هیچ کد مرده ای که دیگه به درد سیستم نمی خوره نباید در بک اند یا فرانت باقی مونده باشه.
