# سند تحلیل مدل داده و فرم‌های کالا — iMach

> **سند مرجع زنده (v0.9 — ۱۳ مهر ۱۴۰۴).** مبنای تحلیل: پروتوتایپ redesign-base فاز ۳۶ (۴۷ صفحه) + بک‌اند imach-back (NestJS/Prisma/MongoDB) + دیتای زندهٔ Atlas (فقط-خواندنی) + اپ Next.js مهاجرت‌یافته برای راستی‌آزمایی قراردادها.
> جایگاه: پیش‌نیاز قفل «قرارداد داده» قبل از فازهای اصلاحی پروتوتایپ (A تا E) و مبنای پرامپت پیاده‌سازی نهایی.
> نسخهٔ قابل ارائه: `download/iMach-Data-Model-Analysis-v0.9.docx`

## ۰. جمع‌بندی در یک نگاه

- **اسکلت سالم است:** زنجیرهٔ `Good → Product → Listing` با کلید یکتای `(businessId, goodId, variantKey)` دقیقاً «یک کالا با چند بسته‌بندی» صفحهٔ ۰۱ را پشتیبانی می‌کند. تخفیف سه‌سطحی، PriceLog، WatchedGood، Promo، گالری File — همه مدل کامل دارند.
- **۴ شکاف بحرانی:** (۱) رتبه‌بندی قیمت خام بین variantها در موتور تطبیق؛ (۲) توضیحات فروشنده بی‌منبع مدل؛ (۳) مهلت پاسخ‌گویی RFQ بی‌منبع مدل؛ (۴) چسبیدن استعلام به ارزان‌ترین ردیف فروشنده به‌جای variant درخواستی.
- **۲۹ مورد** در ۱۳ فرم/لایه: ۶ بحرانی (C) + ۱۰ مهم (M) + ۱۳ متوسط/جزئی (S). هیچ‌کدام بازطراحی ریشه‌ای نمی‌خواهند.

## ۲. قرارداد واحد قیمت — هستهٔ مسئله

**قرارداد ضمنی فعلی (تأییدشده با دیتا و اپ واقعی):** `priceMinor` به‌ازای `Good.unit` است (برنج SACK → هر گونی؛ پفک KILOGRAM → هر کیلو).

**شکاف:** موتور (`priceRanks` ۰–۱۸ امتیاز + sort نهایی) قیمت خام را بین variantهای مختلف مقایسه می‌کند. مثال واقعی:

| فروشنده | variant | قیمت هر گونی | به‌ازای کیلو | رتبهٔ فعلی | رتبهٔ درست |
|---|---|---|---|---|---|
| پخش برنج پارس | کیسهٔ ۱۰ کیلویی | ۵۹۵٬۰۰۰ | ۵۹٬۵۰۰ | **۱ (ارزان‌ترین!)** | ۴ |
| تجارت گیل‌رنج | نامشخص* | ۲٬۷۸۰٬۰۰۰ | ۵۵٬۶۰۰* | ۵ | **۱** |
| پخش برنج پارس | کیسهٔ ۵۰ کیلویی | ۲٬۸۵۰٬۰۰۰ | ۵۷٬۰۰۰ | ۶ | ۲ |

*نیمی از ردیف‌های برنج اصلاً `attrs.weight` ندارند — تبدیل حتی در سطح داده ممکن نیست.

**تناقض مستند:** کامنت مدل `Unit` ادعا می‌کند موتور از `containsQty` برای نرمال‌سازی استفاده می‌کند؛ در `matching.service.ts` هیچ اثری نیست.

**قرارداد چهارماده‌ای پیشنهادی (قفل شود قبل از هر اصلاح فرم):**
1. `Good.unit` واحد رسمی مبادله می‌ماند؛ قیمت/موجودی/حداقل سفارش/حجم همه به این واحد.
2. `Listing.baseQty` عددی جدید = تعداد واحد پایای فیزیکی هر variant (کیسهٔ ۵۰ → ۵۰؛ بدون variant → ۱).
3. `pricePerBaseMinor` در زمان نوشتن محاسبه و ذخیره می‌شود = تنها مبنای رتبه‌بندی/مقایسه (priceRanks، صفحهٔ ۳۳، تابلوی ۰۹، سورت ۳۶).
4. UI آزاد است ورود را به هر واحدی بگیرد ولی همیشه با تبدیل خودکار + نمایش دوگانه («هر کیسهٔ ۵۰ کیلویی ۲٬۸۵۰٬۰۰۰ ≈ هر کیلو ۵۷٬۰۰۰») ذخیره کند.

## ۴. ۰۱ (کاتالوگ) و ۰۲ (جزئیات)

- کارت‌های ۰۱ = variant (نام از Good، زیرعنوان از variantLabel/attrs، قیمت به Good.unit، بج موجود از stock) ✅
- ۰۲: مشخصات/بسته‌بندی/حداقل سفارش/موجودی/گالری ✅؛ توضیحات فروشنده 🔴 (بی‌منبع مدل)؛ تخفیف پلکانی = tiers ✅ (دیتای واقعی)؛ همکار = custPct.h ✅؛ تأمین‌کنندگان ویژه = Promo ✅ ولی مقایسهٔ خام 🔴؛ «آنلاین» بی‌منبع ⚠️؛ fallback وقتی variantLabel=null (۱۱٪) تعریف نشده ⚠️.
- ۰۱: بج «در لیست مقایسه N» بی‌منبع ⚠️ → شمارش WatchedGood یا حذف. نوار «قیمت و موجودی» → ۴۴ ✅ (endpoint گروهی سبک لازم).
- ۰۳: شیت «ویرایش جزئیات» فقط نام/بسته/حداقل سفارش — عکس/توضیحات/کیفیت/اندازه ویرایش‌پذیر نیستند 🔴 (قاعدهٔ ورود=ویرایش نقض).

## ۸. نقشهٔ راه (ضد-حلقهٔ بی‌نهایت)

**شش اصل:** ① قرارداد داده اول ② تعریف قبولی (DoD) هر فاز = بستهٔ شناسه‌ها ③ جهت جریان دیتا: ورود→نمایش→تراکنش ④ سند زندهٔ واحد در گیت ⑤ قاعدهٔ طلایی: هیچ حذفی بدون حکم مالک ⑥ رگرسیون خودکار + چک‌های قرارداد واحد در QA.

| فاز | موضوع | شناسه‌ها |
|---|---|---|
| A | قفل قرارداد + فرم ۰۴ + شیت ویرایش | C2, C5, C6, M1, M6, S5, S8, S13 |
| B | نمایش فروشنده: ۰۱/۲۶/۴۴ | M3, M4, M7, M8, M10, S4, S7 |
| C | نمایش خریدار: ۰۲/۰۹/۱۳/۱۰ | M2, M4, M9, S6, S10 |
| D | تراکنش: ۱۲/۳۳/۳۶ | C1, C3, C4, M5, S1, S2, S9 |
| E | قفل سند ۱.۰ + پرامپت پیاده‌سازی | — |

**تعریف «تمام»:** همهٔ C/M اعمال و QA شده + سند ۱.۰ با امضای مالک قفل + امکان نوشتن پرامپت پیاده‌سازی بدون ابهام (هر فیلد هر فرم → مقصد مدل + برچسب واحد).
