# ۰۸ — سند مهاجرت: از کد فعلی به پیاده‌سازی نهایی imach-final-design

> **جایگاه:** این سند **مرجع مهاجرت از کد عملیاتی فعلی به برنامهٔ نهایی** است — نقشهٔ فازبه‌فازِ پیاده‌سازی پروتوتایپ `prototypes/imach-final-design` (۴۱ فایل اسکرین / ۴۴ نمای منطقی، FD-1 تا FD-45) روی پروژهٔ واقعی (بک‌اند `imach-back` + فرانت‌اند `imach-web`).
> **منبع حقیقت بصری/جریان:** پروتوتایپ + `prototypes/imach-final-design/docs/` (README، design-notes، implementation-notes، design-audit-fixes).
> **منبع حقیقت قرارداد داده:** اسناد `docs/01` تا `docs/06` همین پوشه (به‌روزرسانی‌شده در همین بازه).
> **قاعدهٔ تعارض:** پروتوتایپ در بصری‌ها برنده است؛ سند ۰۳/۰۶ در قرارداد داده برنده است؛ تعارض در جدول «تطبیق‌های آگاهانه» (§۱۰) ثبت می‌شود.
> **تاریخ تدوین:** ۱۴۰۵/۰۷/۳۰ (۲۱ اکتبر ۲۰۲۶) — پس از پول نهایی هر دو ریپو.

## ۰. پروتکل کار با این سند (الزاماً بخوانید)

۱. **این سند چراغ ادامهٔ راه است.** هر نشست پیاده‌سازی از همین سند شروع می‌شود: فاز در جریان را از جدول §۷ پیدا کن، کارها را انجام بده، وضعیت را به‌روز کن، کامیت بزن.
۲. **پایان هر فاز = بسته‌شدن DoD آن فاز** (نه «تا حالا خوبه»). بعد از هر فاز:
   - ستون «وضعیت» جدول §۷ + شمارهٔ کامیت + تاریخ درج می‌شود؛
   - هر انحراف آگاهانه از پروتوتایپ/اسناد در جدول §۱۰ ثبت می‌شود؛
   - کامیتِ مستند با الگوی `docs(migration): M<x> done — <خلاصه>` زده می‌شود.
۳. **سوالات اساسی** (تصمیم محصول/داده که با اسناد و کامنت‌های کد پروتوتایپ قابل استنتاج نیست) → پیاده‌سازی متوقف و از مالک پرسیده می‌شود. سوالات پیش‌وپاافتاده جوابشان در پروتوتایپ، کامنت‌های کد و اسناد ۰۱–۰۷ هست.
۴. **هیچ حذف داده‌ای بدون پروتکل §۵** (بک‌آپ → تأیید → عمل).
۵. نقشهٔ فازهای A→G سند ۰۷ (مسیر تکمیل پروتوتایپ redesign-base) **با این سند منسوخ می‌شود** — آن مسیر مال دورهٔ پروتوتایپ بود؛ این سند مسیر پیاده‌سازی است.

## ۱. تصمیم‌های قفل‌شدهٔ مالک (جلسهٔ ۱۴۰۵/۰۷/۳۰ — عیناً و الزام‌آور)

| # | تصمیم | مفهوم فنی |
|---|---|---|
| D1 | **Tailwind برای همه‌چیز** | کد جدید فرانت ۱۰۰٪ Tailwind (کلاس‌ها در خود JSX). دلیل مالک: خواص منطقی (RTL/LTR) پشتیبانی عالی، خوانایی و دوست‌بودن برای هوش مصنوعی. هیچ فایل CSS حجیم component-محور نوشته نمی‌شود (فقط `@theme` توکن‌ها + استایل‌های سراسری مینیمال). |
| D2 | **چندزبانه = پایه در کد، نه UI چندزبانه** | زیرساخت i18n کاملاً در کد باشد (کانتکست زبان، دیکشنری، `dir`، خواص منطقی CSS) اما UI فقط فارسی. دکمه‌های تغییر زبان فقط در صفحهٔ اول و صرفاً نمایشی. فعال‌سازی واقعی به آینده موکول است (flag سمت سرور) — **لزومی ندارد این موضوع به کاربر گفته شود.** |
| D3 | **چندکشوری فعال** | کاربر هنگام ثبت‌نام کشورش را انتخاب می‌کند — دقیقاً مثل پیاده‌سازی فعلی در اپ واقعی (`intl-phone-field` + `lib/countries.ts`). این مورد در پروتوتایپ جا افتاده و باید در پیاده‌سازی باشد. |
| D4 | **ظاهر نهایی = پروتوتایپ** | با رفع اشکالات ظاهری دسکتاپ و اشکالات منطقیِ شناخته‌شدهٔ پروتوتایپ. همهٔ داده‌ها از دیتابیس/مدل‌ها می‌آیند — فیلد یتیم و دیتای فیک صفر (رفع نقاط کور منطقی با دیتای واقعی). |
| D5 | **خط قرمز داده** | جداول «نوع کالاها» (Good)، «برندها» (Brand)، «کالاها/پروداکت» (Product) و بقیهٔ جداول پایهٔ مرجع (Category، Unit) **نباید دیتایشان از بین برود**. تغییر ساختاری این جداول مجاز است (با پروتکل §۵). بقیهٔ دیتاها (کاربران، دیتای تست و…) مهم نیستند. |
| D6 | **کد قدیمی = مرجع در فولدر جدا** | کد قدیمی فرانت به `legacy/` منتقل می‌شود تا کد جدید تمیز بماند. پس از بالا آمدن کامل پروژهٔ جدید، فایل‌های اضافی و کد مرده چه در بک و چه در فرانت **پاک می‌شوند** (فهرست کامل: §۹). |
| D7 | **کیفیت بین‌المللی + پرفورمنس بیگ‌دیتا** | کش دوطرفه (بک: CacheService/Redis-ready؛ فرانت: React Query)، ویژگی‌های جدید Next.js/React برای سرعت، تحمل رکوردهای میلیونی/میلیاردی (صفحه‌بندی cursor، ایندکس، شمارنده‌های denormalized). کد تمیز، ماژولار، بی‌کدمرده. |
| D8 | **آزادی در تغییر مدل‌ها** | مدل‌ها حتی از صفر قابل بازطراحی‌اند؛ انتظار: بیشتر تغییرها تغییر نام/مفهوم است (مثلاً «ذخیرهٔ کاتالوگ‌شدهٔ مشتری»). هر تغییر با حفظ D5. |

**قوانین همیشگی طراحی (از implementation-notes §۱ — در پیاده‌سازی نقض نمی‌شوند):**
1. مدال/منو/شیت در موبایل **از پایین** باز می‌شود (استثنا: دیالوگ تأیید حذف — «آخرین سؤال»).
2. **تست پیرمرد ۷۰ ساله**: هر طراحی باید برای بازاری سنتی قابل فهم باشد.
3. **همیشه ساده و مینیمال**؛ تزئین اضافه ممنوع؛ ردیف اقدام با صفر = مخفی.
4. **قانون واژگان سه‌سطحی**: گروه کالا > کالا > محصول — «به محصول نگو کالا».
5. فرم ≤۵ فیلد = شیت؛ بزرگ‌تر/چندمرحله‌ای = صفحهٔ مستقل.
6. عدد همیشه تایپ‌شدنی (استپر فقط برای ±۱) — `NumberInput` با نرمال‌سازی ارقام فارسی.
7. قیمت بسته ورودی فروشنده است؛ قیمت واحد محاسبه‌شده — قرارداد واحد-قیمت سند ۰۴.

### ۳.۲. استراتژی بازنویسی و فولدر legacy (D6)

```
imach-web/
├── app/                  ← اپ جدید (از صفر، Tailwind-only)
├── components/           ← کامپوننت‌های جدید (ui/ + imach/)
├── lib/                  ← لایهٔ فنی جدید (api, queries, countries, i18n, format, …)
├── i18n/                 ← زیرساخت زبان (fa فعال؛ en/ar پایه)
├── styles/               ← فقط tokens.css سراسری مینیمال (@theme + base) — یا مستقیم در globals.css
├── legacy/               ← کل اپ قدیمی (مرجع؛ خارج از tsconfig و build)
├── prototypes/           ← دست‌نخورده (منبع حقیقت بصری)
├── docs/                 ← اسناد مهندسی + همین سند
└── qa-app/               ← اسکریپت‌های QA اپ جدید (الگو از qa/ پروتوتایپ)
```

- در **M0** محتوای `app/`, `components/`, `lib/`, `hooks/`, `styles/`, `i18n/`, `lacal-data/` فعلی به `legacy/` منتقل می‌شود (گیت-mv تا تاریخچه حفظ شود) و اسکلت جدید ساخته می‌شود.
- کد سالواح‌شده (§۳.۵) **کپی و پاک‌سازی** می‌شود به ساختار جدید — import از `legacy/` ممنوع.
- `legacy/` در `tsconfig.json` (exclude) و `next.config.ts` نادیده می‌شود؛ فقط خواندنی به‌عنوان مرجع. در M11 با حکم مالک حذف می‌شود.
- `prisma/` اسکلت مردهٔ مخزن وب حذف می‌شود (دسترسی داده فقط HTTP — الگوی موجود).

## ۴. معماری هدف — بک‌اند

### ۴.۱. استراتژی کلی: تکامل افزایشی، نه بازنویسی

بک‌اند فعلی معماری سالم و اثبات‌شده‌ای دارد (۱۳ فاز مهاجرت بدون توقف سرویس). الگوهای حاکم که **ادامه داده می‌شوند**:

- **افزایشی باش:** فیلد جدید nullable + backfill idempotent + کد خوانندهٔ جدید/قدیم.
- **مرجع جهانی find-or-create:** Good/Brand/Product/Unit با `searchText` نرمال‌شده یکتا؛ همگرایی تکراری‌ها.
- **باغبانی PROVISIONAL:** ردیف کاربر-ساخته قابل استفاده، در صف ادمین (تأیید/ادغام/حذف) — وضعیت `ACTIVE|PROVISIONAL|MERGED`.
- **شمارنده‌های denormalized** (catalogCount، viewCount30) + **Snapshot در زمان نوشتن** (currency/city/score روی Offer).
- **enum در مرز API** (class-validator در DTO — Mongo enum بومی ندارد).
- **پول صحیح:** همهٔ مبالغ integer به کوچکترین واحد (ریال)؛ تومان فقط لایهٔ نمایش (÷۱۰).
- **Cursor pagination** روی `_id` برای همهٔ لیست‌ها (سقف الزامی).
- **کش:** CacheService درون‌پردازشی (TTL ۳۰s/60s/5m + Tag + LRU ۵۰۰۰) با اینترفیس ۱:۱ با Redis — همان ادامه می‌یابد + HTTP cache-control روی عمومی‌ها + هدر `x-cache` برای دیباگ.

### فاز M0 — زیرساخت مهاجرت (بدون قابلیت کاربری جدید)

**هدف:** پروژهٔ جدید روی پا، کد قدیمی به‌عنوان مرجع کنار، دیزاین‌سیستم Tailwind آماده، احراز هویت واقعی کار کند.

- **فرانت:**
  1. انتقال اپ قدیمی به `legacy/` (git mv؛ exclude از tsconfig/Next) — §۳.۲.
  2. اسکلت اپ جدید: `app/layout.tsx` (فونت IRANSans + dir از locale — تنها نقطهٔ جهت) · `providers.tsx` (QueryClient + LocaleProvider + auth boot) · `globals.css` فقط `@import tailwindcss` + `@theme` (توکن‌های §۳.۳) + base مینیمال.
  3. کیت UI پایه: `Icon` (اسپرایت پروتوتایپ) · `Sheet`/`Dialog` (موبایل از پایین، دسکتاپ مودال وسچ — ترتیب z §۳.۳) · `Toast` · `Button`/`Input`/`NumberInput`/`SearchSelect`/`Spinner`/`EmptyState` · `AppShell` (data-arm + tabbar موبایل + سایدبار دسکتاپ FD-29) + `AuthGate`.
  4. کپی-پاک‌سازی سالواح‌لیست (§۳.۵): api client · auth-store · countries/iran-geo · i18n (fa کامل، en/ar اسکلت) · format (نرمال‌ساز واحد).
  5. حذف‌های M0 (§۳.۵ آخر) + prune پکیج‌ها.
  6. `qa-app/` با اسکریپت smoke (صفحه بالا، صفر خطای کنسول، dir=rtl).
- **بک‌اند:** فقط بک‌آپ کامل + تست restore + ثبت خط پایه (§۵) — هیچ تغییر اسکیما.
- **DoD:** `npm run build` سبز · ورود/خروج با بک‌اند واقعی کار می‌کند (شیلد AuthGate) · لندینگ اسکلت + شیت دمو در `app/demo` · QA smoke سبز · `legacy/` از بیلد حذف · کامیت ساختار.
